# VS-032 — Builder amigable: gestor visual de formularios con asistente guiado y vista previa

Milestone: post-M12 (roadmap original cerrado en VS-015). Rediseño de experiencia del builder sobre la base del workspace split-view de VS-031: reemplaza el `<select>` plano de tipos de elemento y el editor de tarjetas planas por un asistente guiado (paleta visual + plantillas) con campos en lenguaje natural, secciones colapsables y una vista previa en vivo de cómo verá el formulario el evaluado. Alcance completo (navegación + editor) aprobado por el usuario el 2026-08-13.

VS-031 (workspace split-view con árbol) está implementado y verde en local (typecheck + `builder-publish.spec.ts`) pero **nunca se commitó ni desplegó** — en producción el usuario sigue usando las 5 páginas anidadas y el builder nuevo da 404. ## Especificación previa

Descubrimiento con skills impeccable/ux-architect sobre el código real (subindicator-editor.tsx, builder/page.tsx, runtime page.tsx, componentRegistry, formSchema, engines form/rule/formula):

**Dolores confirmados del editor actual (subindicator-editor.tsx):**
- Picker de elemento = `<select>` plano de 10 tipos técnicos sin contexto (línea 1016) — el creador no sabe cuándo usar cada tipo.
- Labels técnicos en la UI: "Mostrar solo si (ver docs/engines/rule.md)" (473), operador `isAnswered`/`equals` mezclando inglés/español (509), y el UUID crudo `<Pill>{el.id}</Pill>` (445) que el usuario debe copiar para condiciones/fórmulas.
- Fórmula con placeholder críptico `{el-1} + {el-2} * 2` (986) — el usuario adivina qué id es cada pregunta.
- Cards planas con hasta 12 inputs (`tabla_datos`), 3 niveles de sub-opciones — sobrecarga cognitiva, sin jerarquía ni preview.
- Zero representación de cómo se verá el elemento en el runtime (el builder solo edita JSON de config).

**Base técnica para el preview (confirmada por exploración):** el runtime (`apps/web/app/evaluations/[token]/page.tsx`) tiene todo el render módulo-local sin export (ElementView 1115–1397, SubOptionsView 528–574, NaCommentRow 984–1113, etc.), pero **toda la lógica pura ya vive en sdk-core**: `isElementVisible` (rule.ts:13), `evaluateExpression`/`parseFormula` (formula.ts), `deriveStatus`/`isAnswered`/claves sintéticas (response.ts), `questionNumber` (component-registry.ts:41). El preview del builder es render **nuevo** para el builder — se crea como componente propio, no se extrae del runtime (anti-meta: no tocar el runtime público).

## Contratos

### 1. Paleta visual de elementos (reemplaza el `<select>` en `subindicator-editor.tsx:1014-1026`)

- Grid de tarjetas agrupadas por categoría con descripción de uso y ejemplo:
  - **Preguntas**: texto_corto, texto_largo, numero, seleccion_unica, seleccion_multiple, seleccion_desplegable
  - **Contenido**: instruccion, banner
  - **Datos adjuntos**: evidencia, url_publica
  - **Estructurados**: tabla_datos
  - **Automáticos**: calculado
- Cada tarjeta: glifo simple, label humano, descripción (1-2 líneas) y ejemplo (`ej. "Año fiscal 2024"`).
- Abre en drawer/panel sobre el editor (mismo patrón que el modal de confirmación inline existente); ESC/fuera cierra.
- Categorías y descripciones viven en una const local `ELEMENT_PALETTE` (el registry de sdk-core es la fuente de tipos — la paleta es capa de presentación, no duplicar tipos).

### 2. Plantillas de pregunta rápida ("asistente")

- Botones de acceso directo en el header del editor: **"Texto"**, **"Número"**, **"Elección"**, **"Tabla"** — insertan el elemento con defaults sensatos (mismo `newElement`) y lo enfocan (scroll al card recién creado + focus en el input de label).
- El acceso "Agregar elemento completo…" abre la paleta de la sección 1.
- `addingType` (estado actual del select) desaparece; el estado de "insertar" pasa a `{ mode: "quick" | "palette", type }`.

### 3. Campos en lenguaje natural (subindicator-editor.tsx)

- Quitar el `Pill` con UUID del header del card (445): se muestra en su lugar el número de pregunta derivado solo-hasta-ese-punto (`0.1`, `0.2`, … contando solo `isQuestion`; mismo `questionNumber` de sdk-core) o "Contenido" para no-preguntas.
- **Condición de visibilidad** reescrita en lenguaje natural (473-529):
  - Select de elemento destino muestra `Pregunta 0.1 — {primeras 40 chars del label}` (nunca el UUID).
  - Operadores con etiquetas humanas: "tiene respuesta", "no tiene respuesta", "es igual a", "es distinto de", "incluye (selección múltiple)".
  - El bloque completo queda plegado por defecto bajo el resumen colapsable "Condición de visibilidad: siempre visible / solo si…".
- **Fórmula** (979-1008): input + fila de chips "Insertar pregunta" con las preguntas `numero`/`calculado` del mismo subindicador (`label` humaneado y **no** el id); click inserta `{id}` en la posición del cursor. Se mantiene `formulaError` inline.
- Separadores de unidades (602, 924): label pasa a "Unidades separadas por comas".

### 4. Secciones colapsables por elemento (progressive disclosure)

- Cada card de elemento cambia a: header (glifo + tipo + nº + acciones ▲▼Borrar) + secciones plegables Anteriores/Posteriores:
  - "Textos" (label + ayuda + obligatorio) — abierta por default solo si el label está vacío.
  - "Opciones de respuesta" — solo para selecciones/desplegable (incluye sub-opciones anidadas colapsadas una por opción).
  - "Condición de visibilidad" — siempre plegada (resumen en el encabezado).
  - "Avanzado" — límites/unidades/tipos aceptados/máximos, plegada por default.
- Persistencia del estado de plegado por `element.id` en estado local del editor (no en el schema).

### 5. Vista previa del evaluado en vivo

- Nuevo componente `apps/web/components/form-preview.tsx` (client): renderiza el formulario del subindicador **tal como lo ve el evaluado**, sin acceso a red:
  - Inputs: `{ elements: FormElement[] }` (mismo array en edición), `answers: Record<string, AnswerValue>` en memoria.
  - Reutiliza funcionalidad pura de sdk-core: `isElementVisible` (oculta condicionales), `evaluateExpression` para `calculado` (muestra `0.00`/derivado con decimals), `questionNumber` para numeración.
  - Render propio por tipo (campo, select, tabla, banner, instrucción — sin autosave, sin evidencias reales de R2: el lector de evidencia muestra slots vacíos), estilos `field`/`runtime-question` existentes (no se crean tokens nuevos).
  - Toggle "Mostrar todos (ignorar condiciones)" para que el creador vea los elementos que `visibleIf` escondería con respuestas vacías.
- Acceso: botón **"Ver como evaluado"** en el header del editor (junto al estado del autosave) → drawer/dialog a la derecha (móvil: pantalla completa) con mismo patrón CSS de `builder-backdrop`.
- Se actualiza en vivo con cada `commit()` del editor (prop `elements`).

### 6. Flujo de creación guiada de estructura (navegación)

- Empty states del árbol (builder/page.tsx: `EmptyState` 439-515, `builder-nav__empty` 591-593) se reemplazan por **mini-wizard de 4 pasos** para frameworks vacíos: `1. Dimensión → 2. Indicador (opcional, saltar) → 3. Subindicador → 4. Agregar primer elemento`. Cada paso usa los forms inline existentes (`openCreate`/`submitCreate`), con botón "Saltar" solo donde aplica (indicator opcional).
- En el árbol con datos: el EmptyState por dimensión/indicador conserva sus CTA actuales pero con botones con labels completos (ya existen) y texto de ayuda.
- Buscador en el árbol: input arriba del nav ("Buscar…") que filtra subindicadores/dimensiones/indicadores por título (filtro local sobre `dims`, no API).
