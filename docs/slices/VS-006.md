# VS-006 — Builder jerárquico (UI, árbol simple)

Milestone: M3. Primera UI real del proyecto — hasta ahora solo existían rutas API (VS-003, VS-004).

## Especificación previa

`../VISION.md` (flujo ideal del Builder, "cada pantalla resuelve un único problema"), `../domain/evaluation-hierarchy.md` y `../domain/organization-user.md` (ya especificados, no se repiten aquí).

## Contratos

- Cliente de Better Auth (`better-auth/react`, plugin `organization`) en `apps/web/lib/auth-client.ts` — único punto de acceso a sesión/organización desde componentes cliente.
- Sin librería de estilos todavía (Tailwind no está decidido en `../architecture/stack.md`) — HTML semántico mínimo, sin diseño visual elaborado. Esto es una pantalla funcional de verificación, no el diseño final del producto.
- Cada pantalla resuelve un único problema (regla de `../VISION.md`):
  1. `/signup` — crear cuenta.
  2. `/login` — iniciar sesión.
  3. `/organizations` — crear una organización (o listar las propias si ya tiene) y fijarla como activa.
  4. `/frameworks` — listar Frameworks de la organización activa + crear uno nuevo.
  5. `/frameworks/[frameworkId]` — listar Dimensiones de ese Framework + crear una nueva.
  6. `/frameworks/[frameworkId]/dimensions/[dimensionId]` — listar Indicadores + crear uno nuevo.
  7. `/frameworks/[frameworkId]/dimensions/[dimensionId]/indicators/[indicatorId]` — listar Subindicadores + crear uno nuevo + editar título/descripción + borrar.
- Todas las pantallas del Builder (4-7) requieren sesión activa con organización — si no hay, redirigen a `/login` o `/organizations` según corresponda.

## Fuera de alcance (explícito)

- Editor de formulario/elementos dentro de un Subindicador — M4 (VS-007). Un Subindicador en esta UI es solo título+descripción, igual que en VS-004.
- Diseño visual pulido, i18n, WCAG 2.2 AA completo — se revisan en M12. Aquí solo HTML accesible básico (labels, botones semánticos), no un sistema de diseño.
- Edición inline tipo Notion/Airtable (drag-and-drop, atajos) — el objetivo de este slice es verificar el flujo completo funcionando, no la experiencia final del Builder.
- Invitar miembros desde la UI — ya existe la API (VS-003) pero no es parte del flujo mínimo a verificar aquí.

## Hallazgos durante la implementación

- Mismo bug de Turbopack que en VS-004 (imports relativos `.js` hacia `lib/`) — se usó `@/*` desde el principio en este slice.
- `tsconfig.base.json` no incluye la lib `DOM` (proyecto pensado primero para paquetes backend); `apps/web/tsconfig.json` necesitó `"lib": ["ES2022", "DOM", "DOM.Iterable"]` explícito — sin esto, tipos como `HTMLInputElement`/`fetch`/`Response` no resuelven bien y producen errores de tipo confusos (`Property 'value' does not exist on EventTarget & HTMLInputElement`).
- Next.js 16 genera automáticamente `apps/web/AGENTS.md` y `apps/web/CLAUDE.md` en cada `next dev` (avisos de breaking changes de esa versión de Next.js) — se dejaron tal cual y se commitean, es el comportamiento recomendado por el propio Next.js, no compite con la gobernanza de `docs/`.
- Se añadió `components/app-header.tsx` (email + "Cerrar sesión") no especificado explícitamente en el contrato original — sin él no había forma de cerrar sesión desde la UI, un hueco de usabilidad real más que scope creep.
- En dev/Turbopack, la primera visita a cada ruta nueva compila on-demand y puede tardar unos segundos ("Compiling..." visible) — no es un bug, solo hay que esperar la primera vez que se visita cada ruta.
