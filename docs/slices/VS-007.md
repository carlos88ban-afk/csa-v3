## Hallazgos durante la implementación

- **Autosave disparándose sin edición del usuario**: la primera implementación usaba un `useEffect` observando `elements` para disparar el autosave, con un ref `skipNextAutosave` para saltar la carga inicial. Bajo verificación real se detectó que `revisionNumber` subía solo con cargar la página (confirmado reproducible, no artefacto de React Strict Mode). Causa raíz: cualquier `setElements` (incluida la de los datos recién cargados del servidor) disparaba el efecto, y el guard de un solo booleano no cubre correctamente las re-ejecuciones. Rediseñado: el autosave se programa únicamente desde los manejadores de mutación explícitos (`commit()`), nunca desde un efecto reactivo — el fetch inicial ya no puede disparar un guardado por construcción.
- **`Error al guardar` inmediato al agregar un elemento**: `formElement` exigía `label: z.string().min(1)`, pero un elemento recién agregado empieza con `label: ""`. El debounce de autosave fallaba con `VALIDATION_ERROR` antes de que el usuario alcanzara a escribir. Se relajó `label` (y `options[].label`) a `z.string()` sin mínimo — permitir contenido vacío en un borrador es correcto; la validación de "listo para publicar" pertenece a `engine/publishing` (M6), documentado explícitamente en `../engines/form.md`.
- Intento de delegar la implementación del Form Editor a un subagente OpenCode falló por un problema de heredoc de bash específico de este entorno Windows (~35 min, 128k tokens, sin producir el archivo) — se implementó directamente sin ese camino.
