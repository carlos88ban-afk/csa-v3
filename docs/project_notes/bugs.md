### 2026-08-17 - VS-049: drag-and-drop de Indicador/Subindicador no reordenaba nada (evento burbujeado pisaba el estado) [RESUELTO]

- **Issue**: encontrado verificando VS-049 en producción — arrastrar un Indicador (o un Subindicador) sobre otro del mismo nivel no reordenaba nada, sin ningún error visible en consola ni en pantalla. Arrastrar una Dimensión sí funcionaba.
- **Root Cause**: un Indicador vive DENTRO del `div` arrastrable de su Dimensión (misma anidación para Subindicador dentro de Indicador — VS-049 usa drag-and-drop nativo HTML5, no una librería). Los eventos `dragstart`/`dragover`/`drop` son eventos DOM normales que burbujean; sin `stopPropagation()`, al arrastrar un Indicador el evento nativo burbujeaba hasta el `div` arrastrable de la Dimensión contenedora, que TAMBIÉN tiene su propio `onDragStart`/`onDragOver`/`onDrop`. El handler del ancestro se ejecutaba después durante el burbujeo y pisaba el estado compartido `dragScope` con sus propios datos (`{scope: "dim", id: dimensionId}` en vez de `{scope: "ind:...", id: indicatorId}`). El `onDrop` del Indicador (nivel correcto) terminaba llamando a `moveIndicator` con el id de la Dimensión, que no calzaba con ningún hijo (`findIndex` devuelve -1) y no hacía nada — fallaba en silencio, sin lanzar ningún error.
- **Solution**: `e.stopPropagation()` agregado a los 3 handlers (`onDragStart`/`onDragOver`/`onDrop`) en cada uno de los 4 niveles (Dimensión/Indicador/Subindicador/Subindicador directo), más una verificación explícita de `dragScope.scope === <scope esperado>` dentro de cada `onDrop` antes de llamar a la función de mover (antes solo se verificaba el scope en `onDragOver` vía `allowDrop`, que no bloqueaba que `onDrop` igual se disparara con datos de otro nivel). Commit `a9c02f8`, verificado con una secuencia real de `DragEvent` disparada vía JS — persistencia confirmada tras recarga completa en Dimensión e Indicador.
- **Prevention**: cualquier UI con drag-and-drop nativo HTML5 con niveles anidados (un elemento arrastrable dentro de otro elemento arrastrable) necesita `stopPropagation()` en los 3 handlers de drag de CADA nivel — los eventos de Drag and Drop API burbujean igual que cualquier evento DOM, y si dos niveles anidados comparten el mismo state de "qué se está arrastrando", el nivel ancestro pisará el del nivel hijo salvo que se corte la propagación explícitamente. Al verificar drag-and-drop con niveles anidados, probar SIEMPRE el nivel más interno primero (es el más propenso a este bug), no asumir que porque el nivel más externo funciona los internos también.

### 2026-08-17 - `db:push` interactivo sin TTY: workaround para un push aislado dropeó un constraint real (self-inflicted, corregido) [RESUELTO]

- **Issue**: durante VS-049, `drizzle-kit push` pedía confirmación interactiva ("¿truncar `response`?") por un drift preexistente y no relacionado (`response_evaluationId_subindicatorId_unique` nunca aplicado a la Neon real desde que se escribió en el schema). Este entorno no puede responder prompts interactivos (sin TTY). Workaround aplicado: comentar temporalmente el `unique(...)` en `response.ts`, correr el push aislado (solo mis columnas `order` nuevas), restaurar el archivo. **Efecto colateral no anticipado**: al comentar el constraint, drizzle-kit lo interpretó como "constraint a eliminar" y lo DROPEÓ de la Neon real durante ese push — restaurar el archivo después NO deshace un DDL ya ejecutado. Los tests de `response.test.ts` (`upsertResponse ... ON CONFLICT`) empezaron a fallar con `there is no unique or exclusion constraint matching the ON CONFLICT specification`.
- **Root Cause**: asumí que "comentar una línea del schema, pushear, descomentar" era una operación aislada y reversible sin tocar la DB real — pero `db:push` compara el schema TAL COMO ESTÁ EN ESE MOMENTO contra la DB real y aplica el diff de inmediato; el archivo `.ts` no es la fuente de verdad después del push, la DB sí. Restaurar el archivo deja el código coherente con la intención pero NO con la DB real hasta el próximo push exitoso.
- **Solution**: reconstruido el constraint manualmente vía SQL directo (`ALTER TABLE ... ADD CONSTRAINT`), en dos pasos porque el primer intento sin comillas dobles en el nombre lo creó plegado a minúsculas (`response_evaluationid_subindicatorid_unique`, Postgres pliega identificadores no citados) — no coincidía con el nombre exacto que `drizzle-kit` espera (`response_evaluationId_subindicatorId_unique`, camelCase). Recreado citando el nombre correctamente. Verificado con `pg_get_constraintdef` que el nombre, columnas y orden coinciden exactamente con el schema; los 28 tests de `db` (incluidos los 7 de `response.test.ts`) vuelven a pasar.
- **Prevention**: si `db:push` pide confirmación por un drift NO relacionado al cambio que se está haciendo, no comentar/modificar temporalmente el schema para "esquivarlo" — ese drift ya llevaba tiempo sin causar problemas reales (la app funcionaba con el constraint aplicado, solo el archivo `.ts` estaba correcto y la introspección lo señalaba). Alternativas más seguras: (a) aplicar el `ALTER TABLE` del constraint pendiente manualmente primero (resolviendo el drift de raíz, ya que igual hacía falta), (b) usar `--tablesFilter` en `drizzle.config.ts` (cuidado: en esta versión de drizzle-kit el filtro no acota el diff calculado, solo intentó igual crear tablas que ya existían — no confiar en él sin probar antes en un entorno no productivo), o (c) simplemente pedir al usuario que corra el comando interactivo él mismo y responda el prompt. **Nota adicional**: al crear un constraint con nombre camelCase vía SQL crudo (fuera de drizzle-kit), citarlo siempre con comillas dobres (`"nombreExacto"`) — Postgres pliega a minúsculas cualquier identificador sin citar, lo que rompe la coincidencia exacta que `drizzle-kit push` usa para detectar si ya existe.

### 2026-08-15 - Builder: desmarcar "Editable" en una celda `calculado` de `tabla_datos` ocultaba la fórmula y la disfrazaba de contenido fijo vacío [RESUELTO]

- **Issue**: reporte de usuario ("no me está permitiendo Construir tablas similares a esta", con un HTML de tabla que trae una fila total `class="... formula disabled" readonly`) — reproducido paso a paso en producción replicando esa misma tabla (3 filas numéricas + fila "Total board size" con fórmula). Al configurar la celda de la fila total como tipo "Calculado" y luego, siguiendo el impulso natural de marcarla "solo lectura" (coherente con el `readonly` del HTML de referencia), desmarcar la casilla "Editable" en el Builder: la ficha de la celda cambiaba a "Fijo", el selector de Tipo y el campo de fórmula desaparecían por completo, reemplazados por un editor de "Contenido fijo" vacío — la fórmula ya escrita quedaba invisible/inalcanzable desde la UI (aunque no se borraba del dato subyacente). Mismo patrón afectaba Runtime y Preview: una celda `calculado` con `editable: false` se renderizaba como texto estático vacío en vez de evaluar la fórmula.
- **Root Cause**: `editable`/`cellType` se trataban como dos ejes cruzados en vez de reconocer que `calculado` es un tercer modo de renderizado, no una variante de "editable" vs "fijo". En el Builder (`TableConfigEditor`, `apps/web/components/subindicator-editor.tsx`), la rama `{!editable ? <ContenidoFijo/> : <><selectorTipo/>...<FormulaSiCalculado/></>}` anidaba el selector de Tipo (y por tanto el acceso a "Calculado") DENTRO de la rama "editable" — desmarcar la casilla ocultaba ambos. En Runtime (`apps/web/app/evaluations/[token]/page.tsx`, `FormTableView`) y Preview (`apps/web/components/form-preview.tsx`, `PreviewTableView`) el check `if (!editable) return <RichLabel content/>` se evaluaba ANTES del check `if (cellType === "calculado")`, así que cualquier celda calculada con `editable: false` nunca llegaba a evaluarse. El export CSV (`apps/web/app/api/evaluations/[id]/export/route.ts`) tenía el mismo sesgo: `if (!cellCfg || cellCfg.editable === false) return null` habría omitido del CSV una celda calculada marcada no-editable.
- **Solution**: en los 4 archivos, `cellType === "calculado"` ahora se resuelve de forma independiente a `editable` — Runtime/Preview lo chequean antes que `!editable`; el export excluye `calculado` de la condición de skip por `editable === false`; el Builder movió el selector de Tipo fuera de la rama editable/fijo (siempre visible) y, cuando el tipo es "calculado", muestra siempre el editor de fórmula (sin casilla "Editable" ni opción de "contenido fijo", que no aplican a un valor calculado). Al cambiar el Tipo a "calculado" se fuerza `editable: true` explícitamente para normalizar datos previos. 250 tests de `sdk-core` + 28 de `db` siguen en verde (no se tocó el motor de fórmula, solo el cableado de UI/render).
- **Prevention**: cuando un campo booleano (`editable`) y un enum (`cellType`) interactúan, verificar que cada valor del enum tenga sentido cruzado con AMBOS valores del booleano antes de anidar el enum dentro de una rama del booleano — si un valor del enum es conceptualmente ortogonal (como "calculado": ni lo llena el evaluado ni es contenido fijo estático), debe resolverse antes/fuera de esa rama, no dentro. Reproducir bugs de Builder siguiendo el flujo exacto que un usuario real seguiría (incluir el paso "marcar como solo lectura" cuando el HTML de referencia trae `readonly`), no solo el camino feliz que ya se verificó al cerrar el slice original.
- **Verificación en producción (2026-08-15)**: commit `10d6fe1` + push a `main`, deploy Vercel `dpl_FxU5Py3avjA2wfSujuqLWZFScuei` READY (esta vez el webhook GitHub→Vercel disparó el build automáticamente, sin demora). En el framework temporal `csa-v3-web.vercel.app`, la misma celda que había quedado con `editable: false` durante la reproducción del bug (antes del fix) mostró, tras recargar con el fix desplegado: ficha "Calculado" (no "Fijo"), panel expandido con Tipo="Calculado" y el campo Fórmula con la expresión ya guardada intacta y visible (dato nunca se había corrompido, solo quedaba oculto). Vista previa del Builder: fila "Total board size" mostraba "(sin calcular)" antes de llenar datos, luego **12** en vivo al escribir 4/6/2 en las tres filas numéricas.

### 2026-08-15 - Runtime/preview: radio/checkbox de opción con label en la línea siguiente al control [RESUELTO]

- **Issue**: en producción, el radio/checkbox de una opción/sub-opción quedaba solo en su línea y el texto del label caía a la línea siguiente — reportado por el usuario como "muy confuso" al probar VS-046, pero afecta a CUALQUIER opción con label enriquecido (no es específico de VS-046).
- **Root Cause**: `<label className="field--checkbox">` en `apps/web/app/evaluations/[token]/page.tsx` (Runtime, 4 sitios) y `apps/web/components/form-preview.tsx` (preview del Builder, 3 sitios) nunca tenía la clase base `field` — solo `.field` define `display: flex`, y `.field--checkbox` (sin `.field`) solo aporta `flex-direction`/`align-items`/`gap`, que son no-ops sin `display: flex`. El Builder (`subindicator-editor.tsx`) sí combinaba correctamente `"field field--checkbox"` en sus 3 usos, por eso ahí se veía bien. Sin `display: flex`, el `<label>` queda `display: inline` (o blockificado por un padre flex, según el caso) y el `<p>` que envuelve el label desde VS-045 (el editor TipTap siempre wrappea texto en `<p>`, incluso para una sola línea) fuerza el salto de línea como cualquier bloque dentro de flujo normal. Antes de VS-045 (labels en texto plano, sin `<p>`) el bug existía en el DOM pero era invisible: texto plano inline no fuerza salto de línea.
- **Solution**: `className="field field--checkbox"` en los 7 sitios de Runtime/preview (mismo patrón que ya usaba el Builder) — commit `07b74d8`.
- **Prevention**: `.field--checkbox` está diseñado para combinarse SIEMPRE con `.field` (aporta solo el override de `flex-direction`/`align-items`, no `display`) — al agregar un nuevo `<label className="field--checkbox">` en cualquier archivo, verificar que también lleve `field`. Un lint de clases CSS o un componente compartido (`<CheckboxField>`) evitaría que se repita.
- **Nota operativa**: al desplegar este fix, el push a `main` no disparó un deploy automático en Vercel (~8 minutos sin nuevo deployment pese a que GitHub confirmaba el commit en `origin/main`) — causa no determinada (posible demora puntual del webhook GitHub→Vercel). Se resolvió disparando manualmente "Create Deployment" → pegar el SHA del commit → "Deploy to Production" desde el dashboard de Vercel. Si un push no aparece en `list_deployments` después de 1-2 minutos, no seguir esperando: usar este mecanismo en vez de re-pushear o esperar indefinidamente.

### 2026-08-15 - Runtime VS-045: el select de referencia flexible (URL/Documento) revertía a "URL pública" al cambiarlo [RESUELTO]

- **Issue**: en producción, al cambiar el mini-select de un slot de referencia flexible de "URL pública" a "Documento interno", el select volvía inmediatamente a "URL pública" y el slot seguía mostrando el input de URL — imposible subir un documento interno. Hallado en la verificación en producción de VS-045 (evaluación `lqXXMxax9vayHuXV-BHqcBy5NhUTGAzi`).
- **Root Cause**: dos derivaciones del mismo error en `apps/web/app/evaluations/[token]/page.tsx` (`OptionReferencesView`): (1) el `value` del select se derivaba solo del slot (`isDocRef(slot) ? "doc" : "url"`), pero `changeKind("doc")` vacía el slot a `null` — un slot `null` es indistinguible de "URL aún sin texto", así que el select revertía a "URL pública"; (2) el branch de render (input URL vs file input) usaba la misma derivación `isDocRef(slot)`, con lo que ni siquiera el input cambiaba, y si lo hubiera hecho, `slot.name` sobre `null` habría crasheado.
- **Solution**: estado local `pendingKinds: ("url" | "doc")[]` por índice, sincronizado en `changeKind`/`removeSlot`; el select y el branch de render ahora usan `kindOf(index)` (slot docRef → "doc", string → "url", vacío → pendingKind), y el branch doc con slot vacío muestra "Selecciona un archivo para adjuntarlo como documento interno." (commit `1a5fd0d`, tras `7d745c8` que solo cubrió el select).
- **Prevention**: cuando un mini-select de tipo gobierna el render de su propio slot y el valor de tipo no es derivable del contenido (slot vacío), el tipo elegido debe ser estado propio del componente, no una función del contenido; verificar en producción con el flujo completo (cambiar tipo → subir archivo → recargar → persistencia), no solo el cambio de select.

### 2026-08-14 - Preview del Builder trataba sub-opciones de nivel 1 como excluyentes, el Runtime real como múltiples [RESUELTO]

- **Issue**: `apps/web/components/form-preview.tsx` (`PreviewSubOptions`, preview en vivo del Builder) renderizaba las sub-opciones de nivel 1 como `type="radio"` (excluyentes) mientras `apps/web/app/evaluations/[token]/page.tsx` (`SubOptionsView`, Runtime real) las renderizaba siempre como `type="checkbox"` (múltiples), sin importar el nivel. Encontrado al implementar VS-040 (analizando el HTML real de S&P, que confirmó que S&P sí usa grupos excluyentes en algunos casos anidados).
- **Root Cause**: `PreviewSubOptions` decidía el comportamiento a partir del nivel de anidamiento (`level === 1 ? "radio" : "checkbox"`), una heurística fija desde VS-016, en vez de un campo explícito del schema. `SubOptionsView` nunca implementó esa heurística y quedó siempre en checkbox. Ninguno de los dos estaba "mal" en sí — simplemente no había un campo del schema que gobernara el comportamiento, así que cada componente asumió algo distinto.
- **Solution**: VS-040 agrega `formOption.subOptionsExclusive?: boolean` (default `false`) — ambos componentes ahora leen el mismo campo explícito en vez de asumir por nivel o quedar fijos en checkbox. Sin impacto en datos guardados: el preview del Builder nunca persiste respuestas (es efímero), y el comportamiento por defecto (`false`) preserva el checkbox que el Runtime real ya usaba.
- **Prevention**: cuando un comportamiento de UI depende de "qué tipo de grupo es esto", modelarlo como campo explícito del schema desde el principio, no como heurística implícita (nivel de anidamiento, posición, etc.) — evita que dos componentes que renderizan la misma estructura diverjan silenciosamente.

### 2026-08-14 - E2E `builder-publish.spec.ts`: wizard del builder no reconoce una Dimensión recién creada como seleccionada [RESUELTO]

- **Issue**: al correr el e2e completo (Framework → Dimensión → Builder → Indicador → ...), tras crear una Dimensión y navegar a `/builder?s=<dimId>` (URL correcta, confirmada), el panel derecho muestra el asistente de 4 pasos (VS-032) todavía en el paso 1 "Dimensión" con el botón "Crear dimensión" — nunca aparece el botón "Crear indicador" que el test espera para una dimensión ya creada y seleccionada, aunque el árbol de la izquierda sí muestra la dimensión correctamente expandida con "Sin indicadores todavía".
- **Root Cause**: dos bugs distintos en `apps/web/app/frameworks/[frameworkId]/builder/page.tsx`, ambos con la misma raíz — el estado del builder no se sincroniza correctamente con datos reales cuando se llega por una navegación FRESCA (carga completa de página con `?s=` ya en la URL), a diferencia de una selección hecha en vivo dentro del builder ya montado:
  1. `resolveFocus(tree, raw)` — cuando `raw` coincidía con una Dimensión/Indicador real pero sin subindicadores todavía, la función "caía" al default global (primer subindicador de TODO el árbol) en vez de reconocer que `raw` sí era un nodo válido sin hijos. Reproducido a mano: navegar directo a `/builder?s=<idDimensiónVacía>` en un framework con otras dimensiones existentes selecciona silenciosamente un subindicador no relacionado.
  2. `wizardStep` arrancaba siempre en `0` en cada montaje fresco del builder, sin importar si la Dimensión ya existía (creada momentos antes desde `/frameworks/[id]`, una página distinta) — el único mecanismo que avanzaba `wizardStep` era un efecto atado a `treeMessage`, que solo dispara por altas hechas DESPUÉS de montado el builder, no por datos que ya venían cargados.
- **Solution**: `resolveFocus` reescrita para devolver `null` explícito (no el default global) cuando `raw` coincide con una Dimensión/Indicador real vacío — el llamador ya tenía el fallback correcto (`focusId = resolved ?? initialRaw`). Nuevo `useEffect` que sincroniza `wizardStep` a partir del árbol real (`dims`) apenas carga, no solo vía eventos de `treeMessage`. Verificado con el mismo e2e: el punto de falla original desaparece por completo.
- **Prevention**: cualquier estado derivado de "qué está seleccionado/en qué paso vamos" en una página que puede montarse fresca con query params (`?s=`) debe derivarse de los datos reales al cargar, no solo de eventos que ocurren en vivo dentro de la misma sesión de montaje.

### 2026-08-14 - Builder (VS-032) roto en producción: `ReferenceError: window is not defined` en SSR

- **Issue**: usuario reportó que las actualizaciones de VS-032 no se veían en producción. La página `/frameworks/[frameworkId]/builder` fallaba en el render de servidor (confirmado vía `mcp__plugin_vercel_vercel__get_runtime_errors`: 11 ocurrencias desde el deploy del commit `c285c50`/VS-032, todas contra el deployment vigente). El deploy en sí estaba correcto (alias de producción apuntaba al commit `9e016a4`, `state: READY`) — el bug era puramente de código.

Aunque el componente es `"use client"`, Next.js sigue renderizando el HTML inicial en el servidor — y el inicializador lazy de `useState` corre en ese primer render, donde `window` no existe. - **Solution**: `treeOpen` arranca en `true` (valor fijo, seguro en servidor) y un `useEffect` nuevo ajusta el valor real con `window.matchMedia` tras montar en cliente. `pnpm --filter web typecheck` y `pnpm --filter web build` verificados en verde tras el cambio.
- **Prevention**: ningún inicializador de `useState` (`useState(() => ...)`) puede leer `window`/`document`/`localStorage` — ese código corre durante SSR incluso en componentes `"use client"`. Ese acceso siempre va en un `useEffect` (con un valor por defecto seguro para el primer render) o detrás de un guard `typeof window !== "undefined"`. Al añadir una feature de builder/runtime nueva, revisar `mcp__plugin_vercel_vercel__get_runtime_errors` (no solo `list_deployments`) para confirmar que no hay errores de servidor silenciosos — el deployment puede estar "READY" y la ruta puede seguir rota en tiempo de ejecución.

### 2026-08-13 - E2E public-runtime: el comentario en negrita (TipTap) no sobrevive al reload — autosave de montaje pisando la respuesta
- **Issue**: `e2e/public-runtime.spec.ts` (VS-030) falla siempre: tras escribir un comentario con negrita y recargar la página, el comentario aparece vacío (el `<strong>` no persiste). Reproducido 3/3 en local **y confirmado en producción** (2026-08-13, Chrome DevTools MCP sobre `csa-v3-web.vercel.app`): tras el reload, el PUT de montaje (body `{"answers":{"el-0-0":"42",...,"el-0-0::comment":"<p></p>",...}}`) llega con el `::comment` vacío y sobrescribe el comentario con negrita — el snapshot post-reload muestra el editor vacío.
- **Root Cause**: (diagnóstico por trace de Playwright, línea de tiempo real de requests) el servidor SÍ persiste el bold correctamente — el PUT del evaluado con `<p><strong>Texto en negrita</strong></p>` devuelve 200 con la fila guardada. El problema es un segundo PUT que ocurre tras el reload: al montarse el editor TipTap con `content` vacío, `onUpdate` se dispara durante el `setContent` inicial → `setAnswer` → `dirtySubRef` → autosave (debounce 1500ms) con un `answers` parcial que contiene SOLO los keys `::comment` vacíos (sin `el-texto`/`el-unica`, que aún no se han hidratado porque el GET `/responses` tardó ~9.6s). - **Solution**: pendiente (no fijado aún; opciones: no disparar autosave en el `onUpdate` de montaje del editor, o fusionar `answers` del PUT con el estado previo en el server en vez de sobrescribir, o esperar la hidratación antes de permitir el primer autosave).
- **Prevention**: cualquier autosave que se dispare desde eventos de montaje de un editor (TipTap `onUpdate` al `setContent`) debe comprobar si el subindicador ya fue hidratado con respuestas del servidor antes de escribir; y los PUT de autosave no deberían contener `answers` parciales sin merge server-side.

### 2026-08-07 - Editor WYSIWYG (VS-030) pierde el foco justo después de ganarlo
- **Issue**: Al reemplazar el `<textarea>` del comentario confidencial por un editor TipTap (`contentEditable`), un click dentro del editor lo enfocaba correctamente por un instante (confirmado con `document.activeElement`) pero perdía el foco de inmediato — el texto tecleado terminaba en el `<input>` principal de la pregunta ("Nombre del responsable"), no en el editor. Reproducido de forma inconsistente en local (Playwright/`next dev`) antes de aislarse; confirmado y corregido probando contra producción real.
- **Root Cause**: `NaCommentRow` vivía dentro del mismo `<label className="field runtime-question">` que el input principal de la pregunta (texto_corto/texto_largo/número/seleccion_desplegable). Un `<label>` redirige el foco/activación a su control asociado ante *cualquier* click dentro de él — comportamiento nativo del navegador (HTML Living Standard), no un bug de React — salvo que el elemento clickeado ya sea él mismo un control de formulario nativo que intercepta su propio click (`input`/`textarea`/`select`/`button`). El `<textarea>` anterior (VS-028) nunca mostró el problema porque, siendo un control nativo, quedaba exento de esa redirección; un `contentEditable` no lo es.
- **Solution**: Restructurados los 4 tipos de elemento afectados (`texto_corto`, `texto_largo`, `numero`, `seleccion_desplegable` en `apps/web/app/evaluations/[token]/page.tsx`): el `<label>` ahora envuelve *solo* su propio control (label + input); `naCommentRow`/`statusRow` quedan como hermanos fuera de él, dentro de un `<div className="field runtime-question">` que conserva el mismo estilo. De paso resuelve la ambigüedad de accesibilidad preexistente (el input principal y el comentario compartían accessible name vía el `<label>` compartido).
- **Prevention**: Cualquier elemento interactivo no-nativo (`contentEditable`, componentes custom con `tabIndex`) que se agregue dentro de un `<label>`/`<fieldset>` existente debe verificarse contra este comportamiento — un `<label>` nunca debe envolver más de un control real. Si aparece de nuevo, sospechar primero del wrapper antes de asumir un bug de event handling en React.

### 2026-08-04 - Build de Vercel falla con "DATABASE_URL is not set" pese a estar configurada en el proyecto
- **Issue**: Al desplegar `apps/web` en Vercel (primer despliegue, adelantado antes de VS-009), `turbo run build` falla en `/api/dimensions/[id]` con `DATABASE_URL is not set`, aunque la variable sí estaba puesta en Settings → Environment Variables de Vercel.
